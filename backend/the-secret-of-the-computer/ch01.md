# 프로그래밍 언어부터 프로그램 실행까지, 이렇게 진행된다.

# Part 1. 핵심 용어 정리

## 1단계: 코드 작성
**목적: 인간이 이해할 수 있는 언어로 프로그램 로직 표현**

- 소스파일 - 프로그래머가 작성한 원본 코드 파일
- 고급 언어 - 인간이 이해하기 쉬운 프로그래밍 언어 (C, Java 등)
- Statement(문) - 프로그래밍 언어의 한 문장
- 구문(Syntax) - 언어의 문법 규칙과 논리적 패턴
- 매개변수 - 함수의 동작을 다르게 만드는 입력값
- 헤더 파일 - 함수 선언 등을 담은 참조용 파일

---

## 2단계: 컴파일 (번역 과정)
**목적: 인간의 언어를 컴퓨터가 이해할 수 있는 기계어로 번역**

**컴파일러** - 고급 언어를 기계어로 번역하는 프로그램

### 컴파일러 내부 동작 순서:
1. **토큰** - 코드를 의미 단위로 잘게 쪼갠 조각
2. **어휘 분석** - 토큰을 추출하는 첫 단계
3. **구문 분석** - 문법이 맞는지 검사
4. **구문 트리** - 코드 구조를 나무 형태로 표현한 것
5. **의미 분석** - 문법적으로 맞지만 논리적 오류가 있는지 확인
6. **중간 코드** - 최적화를 위한 중간 형태 코드
7. **최적화** - 코드를 더 빠르고 효율적으로 개선
8. **어셈블리어** - 기계어에 가까운 저수준 언어 (인간이 읽을 수 있는 수준)
9. **기계어** - CPU가 직접 실행할 수 있는 0과 1의 명령어

**대상파일(Object File)** - 컴파일 결과물 (아직 실행은 안 됨)

---

## 3단계: 링크 (파일 합치기)
**목적: 분리된 코드 조각들을 하나의 실행 가능한 프로그램으로 통합**

**링커(Linker)** - 여러 대상파일을 하나로 합치는 도구

### 링커가 하는 일:
- **심벌(Symbol)** - 전역변수와 함수의 이름
- **심벌 테이블** - 각 파일이 제공하고 참조하는 심벌 목록
- **심벌 해석** - 각 심벌이 딱 한 곳에만 정의되었는지 확인
- **종속성** - 파일 간 의존 관계
- **인터페이스** - 모듈끼리 소통하는 방식

### 라이브러리 연결:
- **정적 라이브러리** - 실행파일에 코드를 직접 복사해 넣음
- **동적 라이브러리** - 나중에 참조할 정보만 저장

**재배치(Relocation)** - 임시 주소를 실제 메모리 주소로 바꾸기  
**독립 코드(PIC)** - 어디에 적재되든 작동하는 코드  
**실행파일** - 최종 결과물 (예: .exe)  
**_start** - 프로그램 시작점을 알려주는 특수 심벌

---

## 4단계: 메모리 적재 (실행 준비)
**목적: 디스크에 있는 실행파일을 메모리로 올려 실행 준비 완료**

**로더(Loader)** - 실행파일을 디스크에서 메모리로 복사하는 도구

### 동적 라이브러리 연결 (2가지 방식):
- **적재 중 동적 링크** - 프로그램 시작할 때 라이브러리 연결
- **런타임 동적 링크** - 실행 중 필요할 때 연결 (예: 플러그인)
- **플러그인** - 실행 중 동적으로 추가되는 기능 모듈
- **API** - 런타임 링크에 사용하는 프로그래밍 인터페이스

---

## 5단계: 실행 (메모리에서 동작)
**목적: 프로그램이 안전하고 효율적으로 메모리를 사용하도록 공간 할당**

### 가상 메모리 구조 (위→아래 순서):
- **가상 메모리** - 각 프로그램이 독점한다고 착각하는 가짜 메모리 공간
- **스택 영역** - 지역변수, 함수 호출 정보 (상위 주소)
- **힙 영역** - 프로그래머가 직접 할당하는 동적 메모리
- **데이터 영역** - 전역변수 저장
- **코드 영역** - 실행할 기계 명령어 저장 (하위 주소)

### 실제 메모리 매핑:
- **물리 메모리** - 실제 RAM 하드웨어
- **메모리 페이지** - 메모리를 관리하는 단위 블록
- **페이지 테이블** - 가상 주소 ↔ 물리 주소 변환표

---

## 6단계: CPU 실행
**목적: 메모리에 적재된 기계어 명령을 실제로 처리하여 프로그램 동작**

**CPU** - 명령어를 실제로 처리하는 하드웨어  
**트랜지스터** - CPU를 구성하는 전자 스위치

### CPU 동작 방식 (2가지):
1. **직접 실행** - CPU가 기계어를 직접 처리
2. **VM(가상 머신)** - CPU를 소프트웨어로 시뮬레이션  
   **인터프리터** - 코드를 한 줄씩 읽어 실행 (VM 방식)

---

# Part 2: 의문점 정리 

## 정적 링크 VS 동적 링크 

### 정적 링크(Static Link) VS 동적 링크(Dynamic Link)

**정적 링크**는 컴파일 단계에서 라이브러리 코드를 실행 파일에 직접 복사하여 포함시키는 방식입니다.

**동적 링크**는 정적 링크와 달리 프로그램이 실행될 때(런타임) 링크가 일어나는 방식입니다. 실행 파일을 메모리에 적재(loading)할 때 동적 라이브러리에 의존하는지 확인하며, 의존할 경우 동적 링커(dynamic linker)가 실행되어 라이브러리의 메모리 위치와 심벌 주소 등을 확인하는 링크 과정을 수행합니다. 동적 링크는 프로그램이 종료될 때까지 (실행 시간 CPU가 프로그램을 실행하기 시작하는 시점부터 실행이 완료되어 프로그램이 종료될 시점까지) 지속될 수 있습니다.

---

### 심벌 해석 과정 (Symbol Resolution Process)

심벌 해석(symbol resolution)은 링커가 특정 심벌(변수나 함수)에 대한 실행 시점의 메모리 주소를 결정하는 과정입니다.

1.  **심벌 정보 기록:** 컴파일러는 심벌 정보를 심벌 테이블(symbol table)에 기록합니다. 심벌 테이블에는 해당 모듈에서 정의된 심벌과 다른 모듈에서 사용되는 외부 심벌 정보가 포함됩니다.
2.  **주소 임시 지정:** 컴파일러는 함수를 호출하는 `call` 명령어 등을 생성할 때, 해당 함수가 메모리 어느 주소에 적재될지 모르기 때문에 일단 임시로 주소를 $0x00$과 같이 지정해 둡니다.
3.  **링커의 역할:** 링커는 대상 파일(object file)들을 결합하여 실행 파일을 생성할 때, 심벌 해석 과정을 통해 이 임시 주소를 최종 실행 메모리 주소로 수정해야 합니다.
4.  **재배치 정보 사용:** 링커는 컴파일러가 남긴 재배치 정보(예: `.rela.text`, `.rela.data`)를 이용하여 $0x00$으로 지정된 심벌의 위치를 찾아내고, 해당 심벌의 최종 메모리 주소로 명령어의 오프셋을 수정합니다.

---

### 재배치(Relocation)가 필요한 이유

**재배치(relocation)** 는 심벌의 주소를 실행 시점의 메모리 주소로 수정하는 과정입니다.

재배치가 필요한 근본적인 이유는 프로그램이 실행된 후 **기계 명령이 메모리 주소를 확인**해야 하기 때문입니다.

컴파일러는 소스 파일을 컴파일할 때 변수나 함수의 실행 시점 메모리 주소가 어디에 위치할지 정확히 알 수 없습니다. 따라서 컴파일러는 임시 주소($0x00$ 등)를 사용하고, 링커가 실행 파일을 생성할 때 심벌의 최종 메모리 주소를 결정하여 해당 주소를 수정하는 작업이 필수적입니다.

---

### 정적 vs 동적 라이브러리 비교

| 특징 | 정적 라이브러리 (Static Library) | 동적 라이브러리 (Dynamic Library / Shared Library) |
| :--- | :--- | :--- |
| **링크 시점** | 컴파일 및 링크 시점 | 프로그램 실행 시점 (런타임) |
| **코드 포함 방식** | 실행 파일에 라이브러리 코드가 직접 복사됨 | 실행 파일에는 필요한 정보만 저장되고, 라이브러리 코드는 별도 파일(.so, .dll 등)로 존재 |
| **디스크/메모리 효율** | 여러 프로그램이 사용 시 코드 중복으로 디스크 및 메모리 낭비 발생 | **코드 공유**가 가능하여 메모리 및 디스크 자원 절약 |
| **수정 용이성** | 라이브러리 코드가 변경되면 관련 프로그램 전체를 재컴파일해야 함 | 라이브러리 파일을 교체하는 것만으로 업데이트 및 버그 수정 가능 (재컴파일 불필요) |
| **종속성 문제** | 없음 (모든 코드가 실행 파일 내부에 있으므로) | 라이브러리가 없거나 버전이 호환되지 않을 경우 프로그램 실행 실패 가능 |
| **기능 확장** | 플러그인(plug-in) 등을 이용한 기능 확장 용이 | |

---

### 왜 주소로 참조할까?

프로그램이 실행될 때, CPU는 **기계 명령어**를 처리하며 이 명령어들은 메모리상의 특정 **주소**를 참조하게 됩니다.

1.  **가상 메모리 체계:** 운영체제는 모든 프로그램에게 표준화된 가상 메모리 공간(예: 코드 영역이 $0x400000$에서 시작)을 제공합니다.
2.  **CPU의 실행 방식:** CPU가 프로그램을 실행하려면 실행에 필요한 기계 명령어를 찾아야 하며, 기계 명령어를 실행할 때 곧바로 주소를 사용해야 합니다. 예를 들어, 함수 호출 명령어(`call`)는 이동할 대상 함수의 정확한 메모리 주소를 필요로 합니다.
3.  **링커의 역할:** 링커의 가장 중요한 역할은 변수나 함수와 같은 심벌 이름을 프로그램 실행 시 CPU가 접근할 수 있는 **구체적인 메모리 주소**로 확정 짓는 것입니다. 이 주소가 최종적으로 확정되어야 프로그램이 오류 없이 실행될 수 있습니다.

---

### 코드 복사 = 정적 링크 정리

**정적 링크(Static Linking)** 는 라이브러리 코드를 **실행 파일에 직접 복사(copy)** 하여 포함하는 방식입니다.

이러한 코드 복사 방식의 특징은 다음과 같습니다:

1.  **통합된 실행 파일:** 대상 파일들(.o 파일)과 정적 라이브러리 코드가 모두 합쳐져 하나의 실행 파일이 생성됩니다.
2.  **중복 문제:** C 표준 라이브러리(C standard library)와 같이 널리 사용되는 라이브러리를 여러 프로그램에서 정적 링크로 사용하면, 모든 프로그램의 실행 파일에 동일한 코드가 복사되므로 디스크 공간과 메모리가 낭비됩니다.
3.  **재배치 필요성:** 정적 라이브러리 코드가 복사되어 프로그램에 종속될 때마다 해당 라이브러리 코드에 대한 재배치 작업이 필요합니다.

# Java 실행의 밑바닥

## Java 프로그램의 실행 과정

### JAR 파일의 정체

**JAR (Java ARchive)** - 여러 `.class` 파일과 리소스를 하나로 묶은 압축 파일

#### JAR의 구조
```
myapp.jar
├─ META-INF/
│   └─ MANIFEST.MF          (메타데이터: 시작점, 버전 등)
├─ com/example/
│   ├─ Main.class           (컴파일된 바이트코드)
│   └─ Service.class
└─ resources/
    └─ application.properties
```

#### C/C++ 실행파일과의 차이
| 특징 | .exe (C/C++) | .jar (Java) |
|------|--------------|-------------|
| **내용물** | 네이티브 기계어 코드 | 바이트코드 (.class) |
| **실행 방법** | OS가 직접 실행 | JVM이 필요 (`java -jar`) |
| **플랫폼 의존성** | 특정 OS/CPU 전용 | JVM만 있으면 어디서나 실행 |
| **크기** | 작음 (코드만) | 큼 (모든 클래스 포함) |

#### MANIFEST.MF의 역할
```
Manifest-Version: 1.0
Main-Class: com.example.Main    ← 프로그램 시작점 지정
Class-Path: lib/library.jar     ← 외부 라이브러리 경로
```

**핵심:** JAR는 실행파일이 아니라 "바이트코드 패키지"이며, JVM이 이를 해석해서 실행

### Gradle/Maven 빌드 과정

Java 빌드 도구 - **컴파일 + 의존성 관리 + 패키징** 자동화

#### Maven 빌드 과정 (`mvn package`)
```
1. [의존성 해결]
   pom.xml 읽기
   → Maven Central에서 라이브러리 다운로드
   → ~/.m2/repository/에 캐싱

2. [컴파일]
   src/main/java/*.java
   → javac 컴파일러 실행
   → target/classes/*.class 생성

3. [리소스 복사]
   src/main/resources/*
   → target/classes/로 복사

4. [패키징]
   target/classes/ 전체를
   → myapp.jar로 압축

5. [테스트 (선택)]
   src/test/java 컴파일 및 실행
```

#### Gradle 빌드 과정 (`./gradlew build`)
```groovy
// build.gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web:3.2.0'
}

tasks.jar {
    manifest {
        attributes 'Main-Class': 'com.example.Main'
    }
}
```

**Gradle의 특징:**
- Maven보다 빠름 (증분 빌드, 빌드 캐시)
- Groovy/Kotlin DSL 사용
- 더 유연한 설정 가능

#### C/C++ 빌드와 비교
| 단계 | C/C++ (Make/CMake) | Java (Maven/Gradle) |
|------|-------------------|---------------------|
| **컴파일** | gcc → 기계어 | javac → 바이트코드 |
| **링크** | ld (링커) 실행 | **없음** (런타임에 수행) |
| **의존성** | 수동 관리 | 자동 다운로드 |
| **결과물** | .exe, .so | .jar |

**핵심:** Java는 빌드 시점에 링크를 하지 않고, 런타임에 JVM이 동적으로 링크

---

### Java의 하이브리드 링크 방식 (정적 + 동적)

Java - "정적처럼 패키징, 동적으로 링크"하는 독특한 방식

#### 정적 링크처럼 보이는 부분
```
myapp.jar
├─ com/example/Main.class       (내 코드)
├─ org/springframework/...      (라이브러리 코드)
└─ META-INF/...
```
- 모든 클래스 파일이 하나의 JAR에 포함
- C/C++의 정적 링크처럼 "코드를 복사"해서 포함

#### 동적 링크로 동작하는 부분

**1. 클래스는 사용 시점에만 로드**
```java
public class Main {
    public static void main(String[] args) {
        // 이 시점까지 MyService는 메모리에 없음
        MyService service = new MyService();  // ← 지금 클래스 로드!
        service.execute();
    }
}
```

**2. 심벌 해석은 런타임에 발생**
```java
// 컴파일 시점: 주소 미확정
public void callMethod() {
    service.process();  // process() 메서드의 주소는?
}

// 런타임: JVM이 동적으로 주소 연결
// 1. MyService 클래스 로드
// 2. process() 메서드의 메모리 주소 확정
// 3. 메서드 호출
```

#### C/C++ 동적 링크와의 비교

**C/C++ 동적 링크 (.dll/.so)**
```c
// 프로그램 시작 시 링크
// printf()의 주소를 libc.so에서 찾아 연결
printf("Hello");  // 주소는 이미 확정됨
```

**Java 동적 링크 (.jar)**
```java
// 클래스 사용 시점에 링크
// MyService의 주소를 JAR에서 찾아 연결
MyService service = new MyService();  // 지금 주소 확정!
```

#### 하이브리드 방식의 장점

| 측면 | 정적 링크 장점 | 동적 링크 장점 |
|------|---------------|---------------|
| **배포** | ✅ 단일 파일 배포 | ❌ 여러 파일 관리 |
| **메모리** | ❌ 코드 중복 | ✅ 필요한 것만 로드 |
| **시작 속도** | ✅ 빠름 | ❌ 느림 (로딩 시간) |
| **유연성** | ❌ 재컴파일 필요 | ✅ 런타임 확장 가능 |

**Java - JAR 안에 모든 코드를 포함(정적)하면서도, 필요한 클래스만 메모리에 로드(동적)하여 균형을 맞춤**

---

### Spring Boot의 Fat JAR 전략 (특수 케이스)

일반 JAR와 달리, Spring Boot - **실행 가능한 Fat JAR** 생성

#### 일반 JAR vs Fat JAR

**일반 JAR (Thin JAR)**
```
myapp.jar
├─ com/example/Main.class
└─ META-INF/MANIFEST.MF
     Class-Path: lib/spring-core.jar lib/tomcat.jar  ← 외부 참조
```
- 실행: `java -cp "myapp.jar:lib/*" com.example.Main`
- 문제: 라이브러리를 별도로 배포 필요

**Spring Boot Fat JAR (Uber JAR)**
```
myapp.jar
├─ BOOT-INF/
│   ├─ classes/              (내 코드)
│   │   └─ com/example/Main.class
│   └─ lib/                  (의존성 라이브러리들)
│       ├─ spring-core-6.0.jar
│       ├─ tomcat-embed-9.0.jar
│       └─ ...
├─ org/springframework/boot/loader/  (커스텀 클래스 로더)
└─ META-INF/MANIFEST.MF
     Main-Class: org.springframework.boot.loader.JarLauncher
```
- 실행: `java -jar myapp.jar` (단 하나의 명령)
- 모든 의존성 포함

#### Spring Boot의 특수 클래스 로더

**문제:** JAR 안에 또 다른 JAR 존재 (BOOT-INF/lib/*.jar)  
**해결:** Spring Boot의 커스텀 클래스 로더

```
1. java -jar myapp.jar 실행
   ↓
2. JarLauncher가 먼저 실행
   ↓
3. BOOT-INF/lib/*.jar를 클래스패스에 추가
   ↓
4. BOOT-INF/classes/에서 Main 클래스 로드
   ↓
5. 애플리케이션 시작
```

#### Fat JAR 생성 방법

**Maven**
```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
        </plugin>
    </plugins>
</build>
```

**Gradle**
```groovy
plugins {
    id 'org.springframework.boot' version '3.2.0'
}
```

`mvn package` 또는 `./gradlew build` 실행 시 자동으로 Fat JAR 생성

#### 장단점

**장점:**
- 단일 파일 배포 (운영 편의성 ↑)
- 의존성 버전 충돌 방지
- `java -jar` 하나로 실행

**단점:**
- 파일 크기가 큼 (50MB~200MB)
- 시작 시간이 느림 (모든 라이브러리 로드)
- 도커 이미지 빌드 시 비효율적 (전체 재빌드)

**해결책: 레이어드 JAR (Layered JAR)**
```
myapp.jar
├─ dependencies/        (거의 안 바뀜)
├─ spring-boot-loader/  (거의 안 바뀜)
├─ snapshot-dependencies/
└─ application/         (자주 바뀜)
```
도커에서 레이어 캐싱 가능 → 빌드 속도 향상

## 런타임 동적 링크 (Java의 핵심)

### 클래스 로딩 메커니즘

**클래스 로딩** - `.class` 파일을 메모리에 올리고 사용 가능한 상태로 만드는 과정

#### 클래스 로딩의 3단계

**1. Loading (적재)**
```
디스크의 .class 파일
    ↓
바이트 배열로 읽기
    ↓
JVM 메모리에 Class 객체 생성
```

**2. Linking (연결)**
- **Verification (검증)** - 바이트코드가 JVM 규칙을 따르는지 확인
  - 매직넘버 확인 (0xCAFEBABE)
  - 스택 오버플로우 체크
  - 타입 안전성 검증
  
- **Preparation (준비)** - static 변수에 메모리 할당 및 기본값 설정
  ```java
  public class MyClass {
      static int count;        // 0으로 초기화
      static String name;      // null로 초기화
  }
  ```
  
- **Resolution (해석)** - 심벌 참조를 실제 메모리 주소로 변환
  ```java
  // 컴파일 시: "MyService.process()" 심벌만 기록
  service.process();
  
  // Resolution 단계: "0x7f8a3c001234" 주소로 변환
  ```

**3. Initialization (초기화)**
```java
public class MyClass {
    static int count = 100;           // 실제 값 할당
    
    static {
        System.out.println("Init!");  // static 블록 실행
        count = 200;
    }
}
```

#### 클래스 로딩 시점 (Lazy Loading)

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("Start");      // Main만 로드됨
        
        MyService service;                // 로드 안 됨 (참조만)
        
        service = new MyService();        // ← 여기서 MyService 로드!
        
        service.process();                // 이미 로드됨, 실행만
    }
}
```

**원칙:** 클래스는 **최초 사용 시점**에만 로드
- `new` 키워드 사용
- static 메서드/변수 접근
- 리플렉션 사용

---

### 클래스 로더의 계층 구조

JVM - **3단계 계층 구조**로 클래스 로드

#### 계층 구조
```
[Bootstrap ClassLoader]  (JVM 내장, C/C++로 구현)
    ↑ 위임
[Platform ClassLoader]   (Java 9+, 구 Extension)
    ↑ 위임
[Application ClassLoader] (사용자 클래스)
    ↑ 위임
[Custom ClassLoader]     (선택적)
```

#### 각 로더의 역할

**1. Bootstrap ClassLoader**
- JVM 핵심 클래스 로드
- 위치: `$JAVA_HOME/lib/` (rt.jar 등)
- 예: `java.lang.*`, `java.util.*`
```java
String.class.getClassLoader();  // null (Bootstrap)
```

**2. Platform ClassLoader (Extension)**
- Java 확장 라이브러리
- 위치: `$JAVA_HOME/lib/ext/`
- 예: `javax.crypto.*`, `javax.xml.*`

**3. Application ClassLoader**
- 사용자가 작성한 클래스
- 위치: `CLASSPATH` 또는 `-cp` 옵션
- 예: `com.example.Main`, Spring Boot 클래스들
```java
Main.class.getClassLoader();  // AppClassLoader
```

#### 위임 모델 (Delegation Model)

**동작 방식:**
```
1. Application이 String 클래스 요청
   ↓
2. "내가 로드하기 전에 부모에게 먼저 물어보자"
   ↓
3. Platform에 위임 → Bootstrap에 위임
   ↓
4. Bootstrap이 String 클래스 로드 성공
   ↓
5. Bootstrap이 반환
```

**장점:**
- 핵심 클래스를 사용자가 덮어쓸 수 없음 (보안)
- 클래스 중복 로드 방지

**예제:**
```java
// 악의적인 시도
package java.lang;
public class String {  // 내 커스텀 String
    // ...
}
```
→ Bootstrap이 이미 로드했으므로 무시됨

#### Spring Boot의 Fat JAR 클래스 로더

```
[Bootstrap ClassLoader]
    ↑
[Platform ClassLoader]
    ↑
[Application ClassLoader]
    ↑
[LaunchedURLClassLoader]  ← Spring Boot 커스텀
    - BOOT-INF/classes/
    - BOOT-INF/lib/*.jar 처리
```

### 심벌 해석 - Java 방식 (런타임)

C/C++와 달리 Java - **런타임에 심벌 해석**

#### C/C++ 방식 (컴파일 타임 링크)
```c
// main.c
void function();  // 선언

int main() {
    function();   // call 0x401000 (링크 시 주소 확정)
}

// lib.c
void function() {
    printf("Hello");
}
```

**링크 단계:**
```
main.o + lib.o
    ↓ [링커]
function의 주소: 0x401000으로 확정
    ↓
실행파일에 "call 0x401000" 기계어 삽입
```

#### Java 방식 (런타임 링크)

**컴파일 결과 (.class 파일)**
```
// javap -c Main.class 출력
0: invokevirtual #2   // service.process() 호출
                       // #2 = 심벌 테이블의 2번 항목
```

**런타임 Resolution:**
```
1. MyService 클래스 로드
   ↓
2. Constant Pool에서 #2 항목 확인
   #2 = MyService.process:()V
   ↓
3. MyService의 메서드 테이블에서 process() 찾기
   ↓
4. 메모리 주소 확정: 0x7f8a3c001234
   ↓
5. 주소로 점프하여 실행
```

#### 메서드 호출의 4가지 방식

**1. invokestatic (정적 메서드)**
```java
Math.max(1, 2);  // 컴파일 타임에 주소 확정 가능
```

**2. invokevirtual (인스턴스 메서드)**
```java
service.process();  // 런타임에 실제 타입 확인 필요
```

**3. invokeinterface (인터페이스 메서드)**
```java
List<String> list = new ArrayList<>();
list.add("test");  // 실제 구현체가 ArrayList인지 LinkedList인지 런타임에 결정
```

**4. invokespecial (생성자, private, super)**
```java
new MyService();  // 생성자 호출
```

#### 동적 바인딩 (Dynamic Binding)

```java
class Animal {
    void sound() { System.out.println("..."); }
}

class Dog extends Animal {
    void sound() { System.out.println("Woof!"); }
}

Animal animal = new Dog();
animal.sound();  // "Woof!" 출력

// 런타임에 실제 타입(Dog) 확인 후 메서드 호출
```

**가상 메서드 테이블 (vtable):**
```
Dog 객체 메모리
├─ vtable 포인터 → [Dog의 메서드 테이블]
│                   ├─ sound() → 0x12345678
│                   └─ ...
└─ 필드 데이터
```

### 리플렉션과 동적 로딩

**리플렉션(Reflection)** - 런타임에 클래스 구조를 조사하고 조작하는 기능

#### 기본 리플렉션

```java
// 1. 클래스 정보 가져오기
Class<?> clazz = Class.forName("com.example.MyService");

// 2. 인스턴스 생성
Object obj = clazz.getDeclaredConstructor().newInstance();

// 3. 메서드 호출
Method method = clazz.getMethod("process", String.class);
method.invoke(obj, "parameter");

// 4. 필드 접근
Field field = clazz.getDeclaredField("privateField");
field.setAccessible(true);  // private도 접근 가능
field.set(obj, "new value");
```

#### Spring의 리플렉션 활용

**1. 컴포넌트 스캔**
```java
@Component
public class MyService { }

// Spring이 하는 일:
// 1. 클래스패스 스캔
// 2. @Component 어노테이션 찾기 (리플렉션)
// 3. 인스턴스 생성 (리플렉션)
// 4. 빈으로 등록
```

**2. 의존성 주입**
```java
@Service
public class UserService {
    @Autowired
    private UserRepository repository;  // private 필드
}

// Spring이 하는 일:
Field field = clazz.getDeclaredField("repository");
field.setAccessible(true);
field.set(userService, repositoryInstance);
```

**3. AOP 프록시**
```java
@Transactional
public void saveUser(User user) { }

// Spring이 하는 일:
// 1. UserService의 프록시 클래스 동적 생성
// 2. saveUser() 호출 시 트랜잭션 시작
// 3. 실제 메서드 호출 (리플렉션)
// 4. 트랜잭션 커밋
```

#### 동적 클래스 로딩

```java
// 플러그인 시스템 예제
public class PluginLoader {
    public void loadPlugin(String jarPath, String className) {
        // 1. JAR 파일을 클래스패스에 추가
        URLClassLoader loader = new URLClassLoader(
            new URL[]{ new File(jarPath).toURI().toURL() }
        );
        
        // 2. 클래스 로드
        Class<?> pluginClass = loader.loadClass(className);
        
        // 3. 인스턴스 생성
        Plugin plugin = (Plugin) pluginClass.getDeclaredConstructor().newInstance();
        
        // 4. 실행
        plugin.execute();
    }
}
```

#### 리플렉션의 성능 비용

```java
// 직접 호출 (빠름)
service.process();  // ~1 nanosecond

// 리플렉션 호출 (느림)
method.invoke(service);  // ~100 nanoseconds
```

**100배 느린 이유:**
- 메서드 검색 오버헤드
- 인자 타입 검증
- 보안 체크
- JIT 최적화 불가

**Spring의 해결책:**
- 빈 생성은 초기화 시 한 번만 (리플렉션)
- 이후 호출은 일반 메서드 호출 (빠름)

## CPU 실행 과정 (JVM 내부)

### JVM의 2단계 실행 전략

JVM - **인터프리터**와 **JIT 컴파일러**를 결합한 하이브리드 방식

#### 전체 흐름
```
바이트코드 로드
    ↓
┌──────────────────────┐
│ 1단계: 인터프리터    │ (즉시 시작)
│   - 한 줄씩 해석     │
│   - 프로파일링 수집  │
└──────────────────────┘
    ↓ (자주 실행되는 코드 감지)
┌──────────────────────┐
│ 2단계: JIT 컴파일러  │ (워밍업 후)
│   - 네이티브 코드 생성│
│   - 최적화 적용      │
└──────────────────────┘
    ↓
CPU 직접 실행 (최고 성능)
```

---

### 인터프리터 모드

**인터프리터** - 바이트코드를 한 명령씩 읽어 즉시 실행

#### 동작 방식
```java
// Java 코드
int sum = 0;
for (int i = 0; i < 100; i++) {
    sum += i;
}

// 바이트코드 (javap -c 출력)
0: iconst_0          // 0을 스택에 푸시
1: istore_1          // sum = 0
2: iconst_0          // i = 0
3: istore_2
4: iload_2           // i 로드
5: bipush 100        // 100과 비교
7: if_icmpge 20      // i >= 100이면 20으로 점프
10: iload_1          // sum 로드
11: iload_2          // i 로드
12: iadd             // sum + i
13: istore_1         // sum = result
14: iinc 2, 1        // i++
17: goto 4           // 4로 점프 (루프)
20: return
```

**인터프리터의 실행:**
```
명령어 0: iconst_0 읽기 → 해석 → 0을 스택에 푸시 → 다음 명령어
명령어 1: istore_1 읽기 → 해석 → 스택에서 pop하여 변수에 저장 → 다음
명령어 2: iconst_0 읽기 → 해석 → ...
(매 명령어마다 해석 과정 반복)
```

#### 장점
- 즉시 시작 - 컴파일 시간 없음
- 낮은 메모리 - 네이티브 코드 생성 불필요
- 프로파일링 - 실행 패턴 수집 가능

#### 단점
- 느린 실행 - 명령어마다 해석 오버헤드
- 같은 코드를 반복 실행해도 매번 해석

---

### JIT 컴파일러

**JIT (Just-In-Time) 컴파일러** - 자주 실행되는 바이트코드를 네이티브 기계어로 변환

#### 기본 동작
```
[바이트코드]
    ↓
[JIT 컴파일러]
    - C1 (Client Compiler): 빠른 컴파일
    - C2 (Server Compiler): 공격적 최적화
    ↓
[네이티브 기계어]
    - x86-64 어셈블리
    - 캐시에 저장
    ↓
[CPU 직접 실행]
```

#### 컴파일 트리거

**메서드 레벨 컴파일:**
```java
void calculate() {  // 이 메서드가 1,500번 호출됨
    // ...
}
// → JIT 컴파일 트리거
```

**루프 레벨 컴파일 (OSR: On-Stack Replacement):**
```java
void process() {
    for (int i = 0; i < 100000; i++) {  // 백점프 10,000번
        // ...
    }
}
// → 루프 실행 중 JIT 컴파일 트리거
```

#### 임계값 (Threshold)

**HotSpot JVM 기본값:**
- 메서드 호출: 1,500회 (Client) / 10,000회 (Server)
- 루프 백엣지: 10,000회

```java
// 예제: 언제 컴파일될까?
for (int i = 0; i < 2000; i++) {
    service.calculate();  // ← 1,500번째 호출 후 JIT 컴파일
}
```

#### 2티어 컴파일 (Tiered Compilation)

```
인터프리터 (Tier 0)
    ↓ (빠르게 시작)
C1 컴파일 (Tier 1-3)
    - 간단한 최적화
    - 프로파일링 계속
    ↓ (더 자주 실행됨)
C2 컴파일 (Tier 4)
    - 공격적 최적화
    - 인라이닝, 루프 최적화 등
```

### 핫스팟(HotSpot) 최적화

JIT 컴파일러 - **프로파일링 데이터 기반 최적화(PGO)** 수행

#### 1. 인라이닝 (Inlining)

**최적화 전:**
```java
int calculate(int x) {
    return add(x, 10);
}

int add(int a, int b) {
    return a + b;
}
```

**최적화 후:**
```java
int calculate(int x) {
    return x + 10;  // add() 호출 제거
}
```

**효과:** 함수 호출 오버헤드 제거 (스택 프레임 생성/파괴 불필요)

#### 2. 루프 언롤링 (Loop Unrolling)

**최적화 전:**
```java
for (int i = 0; i < 4; i++) {
    sum += array[i];
}
```

**최적화 후:**
```java
sum += array[0];
sum += array[1];
sum += array[2];
sum += array[3];
// 루프 제어 오버헤드 제거
```

#### 3. 이스케이프 분석 (Escape Analysis)

**최적화 전:**
```java
void method() {
    Point p = new Point(1, 2);  // 힙 할당
    int x = p.getX();
    // p는 이 메서드 밖으로 나가지 않음
}
```

**최적화 후:**
```java
void method() {
    int p_x = 1;  // 스택 할당 또는 레지스터
    int p_y = 2;
    int x = p_x;
    // 객체 생성 제거 (Scalar Replacement)
}
```

#### 4. 데드 코드 제거 (Dead Code Elimination)

```java
void process(boolean flag) {
    if (flag) {  // 프로파일링: 항상 true
        doSomething();
    } else {
        doOtherThing();  // ← 이 코드는 컴파일에서 제거
    }
}
```

#### 5. 범위 체크 제거 (Range Check Elimination)

```java
int[] array = new int[100];
for (int i = 0; i < 100; i++) {
    array[i] = i;  // 매번 범위 체크?
}

// 최적화: i는 항상 0~99이므로 범위 체크 제거
```

### 바이트코드 → 기계어 변환 과정

#### 단계별 변환

**1. 바이트코드**
```
0: iload_1       // 지역변수 1 로드
1: iload_2       // 지역변수 2 로드
2: iadd          // 덧셈
3: istore_3      // 결과 저장
```

**2. 중간 표현 (HIR: High-level IR)**
```
v1 = Load local[1]
v2 = Load local[2]
v3 = Add v1, v2
Store local[3], v3
```

**3. 저수준 표현 (LIR: Low-level IR)**
```
MOV eax, [ebp-4]   // v1을 레지스터에
MOV ebx, [ebp-8]   // v2를 레지스터에
ADD eax, ebx       // 덧셈
MOV [ebp-12], eax  // 결과 저장
```

**4. 네이티브 기계어 (x86-64)**
```
8B 45 FC        // mov eax, [rbp-4]
8B 5D F8        // mov ebx, [rbp-8]
01 D8           // add eax, ebx
89 45 F4        // mov [rbp-12], eax
```

#### 레지스터 할당

**문제:** CPU 레지스터는 제한적 (x86-64: 16개)

**해결:** 레지스터 할당 알고리즘
```java
// 변수가 많은 경우
int a = 1, b = 2, c = 3, d = 4, e = 5;
int result = a + b + c + d + e;

// JIT가 하는 일:
// 1. 자주 쓰는 변수는 레지스터에
// 2. 덜 쓰는 변수는 스택에 (spill)
// 3. 필요할 때 다시 로드 (reload)
```

#### 성능 비교

```java
// 1억 번 반복 루프
for (int i = 0; i < 100_000_000; i++) {
    sum += i;
}

// 인터프리터: ~5초
// JIT 컴파일 후: ~0.05초 (100배 빠름)
```

## 전체 흐름 요약

```
[개발 단계]
코드 작성 (.java)
    ↓
javac 컴파일 → 바이트코드 (.class)
    ↓
Maven/Gradle → JAR 패키징
    ↓
[실행 단계]
java -jar app.jar
    ↓
JVM 시작 → Bootstrap/Platform/App 클래스 로더 초기화
    ↓
Main 클래스 로드 (Loading → Linking → Initialization)
    ↓
main() 메서드 실행 시작
    ↓
필요한 클래스만 동적 로드 (Lazy Loading)
    ↓
인터프리터로 실행 + 프로파일링
    ↓
핫스팟 감지 (1,500회+ 호출)
    ↓
JIT 컴파일 → 네이티브 기계어 생성
    ↓
CPU에서 직접 실행 (최고 성능)
```
