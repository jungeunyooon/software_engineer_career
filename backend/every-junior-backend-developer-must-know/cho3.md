# 성능과 DB

10초가 넘도록 응답을 받지 못해 에러 발생! 

⇒ 원인은 풀 스캔(full scan)

**풀 스캔**

: 풀 스캔은 테이블의 모든 데이터를 순차적으로 읽는 것을 말한다.  

  보통 쿼리의 where절에 있는 조건에 대응하는 인덱스가 없을 때 풀 스캔이 발생한다. 

  인덱스를 사용하는 것보다 전체 데이터를 탐색하는 것이 더 빠를 때도 풀 스캔이 발생한다. 

DB 성능은 연동하는 모든 서버 성능에 영향을 준다. 

보통은 DB 자체의 문제보다는 DB를 잘못 사용해서 발생한 문제가 더 많다. 

서버 개발자 입장에서 조금만 신경써도 DB 성능 문제를 충분히 줄이거나 없앨 수 있다. 

## 조회 트래픽을 고려한 인덱스 설계

### 예시 상황 : 다수의 사용자가 게시판에서 글을 읽는다.

기능 : 카테고리별로 나눠서 게시글 목록을 보여주는 게시판

```sql
select id, category, writerId, title, content
from article
where category = 10 order by id desc limit 20, 10
```

카테고리 칼럼에 인덱스가 없으면 어떤 일이 벌어질까?

> 1년에 52개의 글, 트래픽(직원수) 1000명, 모든 직원이 5분 이내에 글을 읽는다고 가정
> 
> ⇒ 초당 게시글 읽기 요청 트래픽을 6.67 TPS

> 현재 1000만건의글, (하루에 5000개, 6년이면 1000만건)
> ⇒ 인덱스가 없으면 많은 사용자가 동시에 게시글 목록을 조회하게 되면 카테고리를 비교하기 위해 다수의 풀 스캔이 발생한다. 이로 인해 DB 장비의 CPU 사용률이 100%에 도달하면서 DB가 제 기능을 X 

풀 스캔이 발생하지 않도록 하려면 조회 패턴을 기준으로 인덱스를 설계해야 한다.

⇒ 카테고리별로 게시글 목록을 조회하는 패턴이 존재하므로 카테고리 칼럼에 인덱스를 추가하여 조회 성능 개선

**고려 사항 : DB 테이블을 설계할 때는 조회 기능과 트래픽 규모를 고려해야 한다.** 

### 단일 인덱스와 복합 인덱스

**예시 상황 : 고객 센터에서 특정 사용자의 일자별 활동 내역을 조회하는 activity Log, 일평균 방문 회원은 10만명, 평균 5번의 활동, 하루에 50만건의 데이터, 한달이면 1500만건** 

고객 센터에서 특정 사용자의 일자별 활동 내역을 조회

```sql
select * from activityLog where userId = 123 and activityDate = '2024-07-31'
order by activityDatetime desc
```

성능 문제가 없으려면 userId를 포함한 인덱스가 필요하다. 

**고민할 점은 activityDate를 포함하느냐 하지 않느냐에 대한 것이다.**

> 단일 인덱스: userId만 인덱스로 사용
> 
> 복합 인덱스: (userId, activityDate)를 인덱스로 사용

사용자당 가질 수 있는 데이터가 얼마나 될지 가늠해보면 어떤 인덱스를 사용해야 할지 판단하는데 도움이 된다.

개별 사용자 기준으로 1주일에 하루 방문, 평균 활동 데이터 5건이면 1년이면 260건 → 이정도면 단일 인덱스

몇천 건이 안되는 데이터를 비교하는 시간은 보통 0.1초 이내

매일 방문, 30번 이상의 활동, 1년이면 1만건 → 복합 인덱스 

**특정 일자의 활동 타입별 개수를 구하는 쿼리**

```sql
select activiyDate, activityType, count(activityType)
from activityLog
where activityDate = '2024-07-28'
group by activityType;
```

이 경우에는 데이터를 풀 스캔하지 않으려면 activityDate 칼럼을 인덱스로 사용해야 한다. 

activityDate 칼럼만 인덱스에 존재하면 특정 일자에 해당하는 데이터를 모두 검색해야 한다.

데이터가 적으면 문제가 없지만 하루에 쌓이는 데이터가 수백만 개에 달하면 문제가 생길 수 있다.

이 때는 activityDate 칼럼과 activityType 칼럼을 포함한 복합 인덱스를 적용해야 한다.

이렇게 하면 인덱스에 포함된 값만으로 쿼리 결과를 구할 수 있다. 커버링 인덱스를 사용하면 실제 데이터를 읽지 않기 때문에 조회 시간을 단축할 수 있다.

### 선택도를 고려한 인덱스 칼럼 선택

인덱스를 생성할 때는 선택도가 높은 칼럼을 선택하는 것이 중요하다.

- **선택도의 정의**: 인덱스에서 특정 칼럼의 고유한 값의 비율
- **선택도와 효율성**:
  - **선택도가 높을수록** 칼럼에 고유한 값이 많다는 뜻이며, 인덱스를 이용한 조회 효율이 높다.
  - **선택도가 낮으면** 칼럼에 고유한 값이 적다는 뜻이며, 인덱스 효율이 떨어질 수 있다.
- **예시 (member 테이블)**:
  - `create table member` 테이블은 `memberId`, `gender`, `birthyear` 칼럼을 가진다.
  - `gender` 칼럼은 M, F, N의 3가지 값만 가지므로 **선택도가 매우 낮다**.
  - 만약 `gender` 칼럼에만 인덱스를 사용하고, `gender = 'F'` 조건을 포함하는 쿼리를 실행한다면, 전체 데이터 중 상당 부분을 스캔해야 하므로 인덱스 효율이 떨어진다. 예를 들어, 전체 회원 1천만 명 중 여성이 500만 명이라면, 이 500만 개의 데이터를 확인해야 한다.
  - 따라서 `select * from member where gender = 'F' and birthyear = 1980;` 와 같이 다른 조건과 함께 사용될 때도 `gender` 칼럼만으로는 인덱스 효율이 낮을 수 있다.
- **선택도가 낮아도 유용한 경우 (jobqueue 테이블)**:
  - 선택도가 항상 높아야 하는 것은 아니다. `create table jobqueue` 테이블의 `status` 칼럼은 `W` (대기), `P` (처리 중), `C` (완료) 세 가지 값을 가진다. 대부분의 데이터가 `C` 값을 가지며 `W`와 `P`는 소수이다.
  - 이 경우 `status` 칼럼 자체의 선택도는 낮지만, 실제 쿼리에서는 `where status = 'W'` 같이 특정 값을 조회하는 경우가 많다.
  - `status` 칼럼에 인덱스가 걸려 있지 않으면, `status = 'W'` 조건을 가진 쿼리는 전체 스캔(full scan)을 발생시킬 수 있다. 따라서 작업 큐를 처리하는 코드에서 `W` 상태를 자주 조회한다면, `status` 칼럼을 인덱스에 추가하는 것이 필요하다.

### 커버링 인덱스

커버링 인덱스(Covering Index)는 특정 쿼리를 실행하는 데 필요한 칼럼을 모두 포함하는 인덱스를 의미한다

- **주요 이점**:
    - 커버링 인덱스를 사용하면 **쿼리 효율을 높일 수 있다**.
    - 실제 데이터를 읽지 않고 인덱스만으로 쿼리 결과를 반환할 수 있기 때문에, I/O 작업과 시간을 단축시켜 쿼리 실행 속도를 향상시킨다
- **예시 (activityLog 테이블)**:
  - `activityLog` 테이블에서 `activityDate`와 `activityType` 칼럼을 조회하는 쿼리가 있다고 가정한다
- **일반 인덱스 사용 시**: `where activityDate = '2024-07-31' and activityType = 'VISIT'` 조건으로 데이터를 빠르게 선택할 수 있지만, `SELECT *` 와 같이 선택한 칼럼 외의 다른 칼럼까지 조회하려면 실제 데이터를 읽어와야 한다. 인덱스를 사용하여 조회할 데이터를 선택하는 과정은 빠르지만, 실제 데이터 자체를 읽어와야 한다.
- **커버링 인덱스 사용 시**: `(activityDate, activityType)`을 포함하는 복합 인덱스를 생성하고, `select activityDate, activityType from activityLog where activityDate = '2024-07-31' and activityType = 'VISIT'` 와 같이 쿼리를 실행하면, 필요한 `activityDate`와 `activityType` 칼럼 값이 모두 인덱스에 포함되어 있기 때문에 **실제 데이터에 접근하지 않고도 쿼리가 실행**된다. 이로 인해 실제 데이터를 읽는 과정이 생략되어 쿼리 실행 속도가 빨라진다.

### 인덱스는 필요한 만큼만 만들기

인덱스를 추가하는 것은 항상 좋은 것만은 아니다. **필요한 만큼만 인덱스를 만들어야 한다.**

- **인덱스 추가의 단점**:
    - **성능 저하**: 인덱스를 추가하면 데이터 삽입(INSERT), 변경(UPDATE), 삭제(DELETE) 시 인덱스 관리에도 시간이 필요하므로 **성능이 저하될 수 있다**. 특히 데이터 추가, 변경, 삭제가 빈번한 경우 인덱스 관리 비용이 커진다.
    - **리소스 사용 증가**: 인덱스 자체도 데이터이므로 인덱스가 많아지면 **메모리 및 디스크 사용량이 증가한다**.
    - **오히려 성능 저하**: 하루에 몇 번 발생하지 않는 쿼리나 데이터 수가 수십 건 미만인 경우 인덱스를 추가해도 그 효과가 미미하거나, 오히려 성능이 나빠질 수 있다.
- **복합 인덱스 활용 예시 (activityLog 테이블)**:
    - 시스템에서 자주 사용하는 두 가지 쿼리가 있다고 가정한다.
        
        1. `select * from activitylog where userId = 123 and activityDate = '2024-07-31' order by activityDatetime desc;`
        
        2. `select * from activitylog where userId = 123 and activityDate = '2024-07-31' and activityType = 'BUY' order by activityDatetime desc;`
        
    - 이 두 쿼리를 빠르게 실행하려면 다음 두 가지 복합 인덱스를 만들 수 있다:
        - `(userId, activityDate)`
        - `(userId, activityDate, activityType)`
        - 두 번째 인덱스가 첫 번째 쿼리에도 활용될 수 있지만, 두 번째 쿼리를 최적화하려면 `activityType`까지 포함하는 인덱스가 필요하다.
        - 하지만 하루에 고작 수십 건 미만 발생하는 쿼리에 인덱스를 추가하는 것은 효과가 적고, 오히려 성능에 나쁜 영향을 줄 수 있으므로 신중하게 판단해야 한다.
- **기존 인덱스 재활용 및 변경 고려 (reservation 테이블)**:
    - 새로운 쿼리가 추가될 때 기존에 존재하는 인덱스를 활용할 수 있는지, 또는 요구 사항을 일부 변경하여 인덱스를 활용할 수 있는지 검토해야 한다.
    - `reservation` 테이블에 `reserveDate` 칼럼에 `idxRdate`라는 인덱스가 있다고 가정한다.
    - 만약 `select * from reservation where name = '예약자 이름'` 과 같이 `name` 칼럼으로 조회하는 쿼리가 있다면 `name` 칼럼에 인덱스가 없으므로 전체 스캔이 발생한다.
    - 이때, **요구사항을 일부 변경하여** `reserveDate`와 `name`을 함께 조건으로 사용하는 `select * from reservation where reserveDate = '2024-08-09' and name = '고객명';` 와 같은 쿼리로 변경한다면, 기존 `idxRdate` 인덱스에 `name` 칼럼을 추가하여 복합 인덱스를 만들면 전체 스캔 없이 효율적으로 조회할 수 있다.
- **중복된 칼럼에 대한 인덱스 추가 지양**:
    - 오래 사용하는 DB 테이블에는 기능 추가 과정에서 인덱스가 많아지는 경우가 있다.
    - 만약 동일한 칼럼에 대해 여러 인덱스가 존재한다면, 조회 시 두 인덱스 모두에서 좋은 성능을 보여주는 것이 아니라, **인덱스 관리 비용만 증가**하게 된다.
    - 새로운 인덱스를 추가하기 전에는 **기존에 어떤 인덱스가 존재하는지 확인하고, 동일한 효과를 낼 수 있는 다른 인덱스가 있는지 검토**하는 것이 중요하다.

## 조회 성능 개선 방법

인덱스가 아니여도 조회 성능 개선 방법 존재!

### 미리 집계하기

데이터 조회 시 발생하는 성능 문제를 해결하기 위해 **미리 집계하여 별도 칼럼에 저장하는 방식**을 사용할 수 있다.

- **문제점**: 예를 들어, 설문조사 기능에서 설문별 답변 개수(`answerCnt`)와 '좋아요' 수(`likeCnt`)를 조회하는 쿼리는 논리적으로는 문제가 없지만, 실제 성능 문제가 발생할 수 있다. 30개의 설문이 있고 각 설문마다 평균 답변자 수 10만 명, '좋아요'를 한 회원 수 1만 명이라고 가정하면, 답변 개수와 '좋아요' 수를 세기 위해 총 61번의 `select` 쿼리가 실행된다. 이로 인해 쿼리 실행 시간이 길어지고 트래픽이 몰릴 경우 조회 속도가 급격히 느려질 수 있다.
- **해결책**: 이 경우 `survey` 테이블에 `answerCnt`, `likeCnt`와 같은 집계 칼럼을 추가하고, 답변이 달리거나 '좋아요'를 누를 때마다 **해당 집계 칼럼의 값을 증가시키는 방식**으로 미리 집계할 수 있다.
    - 답변 추가 시: `insert into answer values (...);` 후 `update survey set answerCnt = answerCnt + 1 where surveyId = 아디;`.
    - 좋아요' 취소 시: `delete from liked where answerId = 설문ID and memberId = 회원ID;` 후 `update survey set likedCnt = likedCnt - 1 where surveyId = 설문ID;`.
- **이점**: 미리 집계된 값을 사용하면 설문 목록을 조회할 때 답변자 수와 '좋아요' 수를 세기 위한 별도의 쿼리가 필요 없어져, 서버 처리 시간과 쿼리 실행 시간이 줄어들어 조회 속도가 빨라진다.

### 페이지 기준 목록 조회 대신 ID 기준 목록 조회 방식 사용하기

`OFFSET`과 `LIMIT`를 사용하는 페이지네이션 방식은 데이터 양이 많아질수록 성능 문제가 발생할 수 있다.

- **문제점**: 예를 들어, 총 10만 개의 게시글이 있고 10개씩 페이지를 보여줄 때, 1만 번째 페이지를 조회하는 쿼리(`select id, subject, writer, regdt from article order by id desc limit 10 offset 99990;`)를 실행하면, DB는 99,990번째 ID를 바로 찾지 못하고 **ID 역순으로 99,990개의 데이터를 먼저 세고 나서야 마지막 10개의 데이터를 조회**한다. 이는 시간이 오래 걸리는 작업이다. `deleted` 칼럼과 같이 인덱스에 포함되지 않은 칼럼이 `WHERE` 절에 포함될 경우 실행 시간은 더욱 증가한다.
- **해결책**: **마지막으로 조회한 데이터의 ID를 기준으로 다음 페이지를 조회**하는 방식을 사용한다.
    - 예를 들어, 첫 10개 데이터를 조회한 후 마지막 데이터의 ID가 `9985`였다면, 다음 10개 데이터를 읽을 때는 `select * from article where id < 9985 and deleted = false order by id desc limit 10;`와 같이 쿼리한다.
    - **이점**: 이 방식은 `OFFSET`을 사용하는 경우와 달리 DB가 `9985`보다 작은 ID `9984`를 바로 찾을 수 있으므로 **오프셋으로 필요한 데이터만 세는 과정이 생략되어 실행 시간이 빠르다**. 모바일 화면에서 페이지 이동보다는 스크롤을 통해 다음 데이터를 읽어오는 방식에 잘 어울린다. 프론트엔드 개발자가 추가 데이터 존재 여부를 응답에 포함해 달라고 요청할 경우, 10개가 아닌 11개의 데이터를 조회하여 추가 데이터 여부를 판단할 수 있다.

### 조회 범위를 시간 기준으로 제한하기

조회 성능을 개선하는 또 다른 방법은 **조회 범위를 시간 기준으로 제한하는 것**이다.

- **이점**: 대부분의 기능은 최신 데이터를 위주로 조회하기 때문에, 오래된 데이터까지 모두 조회할 필요가 없는 경우가 많다. 예를 들어, 고객의 점검 결과는 최근 6개월간의 기록만 제공해도 서비스에 문제가 발생하지 않을 수 있다.
- **예시**:
    - 기사 목록을 날짜별로 분류하여 제공할 때, `select title, ... from news where regdt >= '2024-08-09 00:00:00' and regdt < '2024-08-10 00:00:00' limit 100;`와 같이 `regdt` 칼럼에 인덱스를 추가하여 특정 날짜 범위 내의 기사를 조회하면 성능 문제가 발생하지 않는다.
    - `select * from checkResult where cust_id = ? and checkMonth >= ? order by checkMonth desc;`와 같이 쿼리를 단순화하여 최근 데이터만 조회하도록 변경할 수 있다.
- **활용**: 이러한 방식은 쇼핑몰 회원의 주문 내역 조회 기능 등에도 적용될 수 있다. DB의 성능을 높이기 위해 메모리 캐시를 사용하는데, 일반적으로 최신 데이터가 더 많이 조회되므로 조회 범위를 최신 데이터로 제한하면 캐시 효율을 높일 수 있다.

### 전체 개수 세지 않기

목록을 표시할 때 전체 개수를 함께 표시하는 경우가 많지만, `count(*)` 쿼리는 데이터 증가에 따라 실행 시간이 길어질 수 있다.

- **문제점**: `select count(*)` 쿼리는 조건에 해당하는 모든 데이터를 탐색해야 하므로, 데이터가 많아질수록 실행 시간이 증가한다. 커버링 인덱스를 사용하더라도 인덱스 스캔 후 실제 데이터를 모두 읽어야 하는 경우가 있어 속도가 느려질 수 있다.
- **해결책**: 이 문제를 해결하는 방법 중 하나는 **전체 개수를 세지 않도록 프로그램 로직을 변경**하거나, 미리 집계하는 방식(`미리 집계하기` 참조)을 사용하는 것이다. 서비스 담당자와 협의하여 화면에 전체 개수를 표시하지 않는 방향으로 변경할 수 있다.
- **예시**: 특정 검색어에 해당하는 회원 목록을 조회할 때 `select id, ... from member where name like '김은%' order by id desc limit 20;` 쿼리만 실행하고, `select count(*)` 쿼리를 따로 실행하지 않을 수 있다.

### 오래된 데이터 삭제 및 분리하기

데이터 수가 늘어날수록 쿼리 실행 시간이 증가하고, 이는 서비스 속도를 늦추거나 서버 부하를 유발할 수 있다.

- **문제점**: 과거 데이터를 삭제하지 않으면 데이터 수가 계속 늘어나 성능 저하의 원인이 된다.
- **해결책**: **과거 데이터를 삭제하여 데이터 개수를 일정한 수준으로 유지**한다. 예를 들어, 180일 이내의 데이터만 서비스 DB에 유지하고, 181일 이전의 데이터는 별도의 저장소로 분리 보관할 수 있다. 이는 서비스 품질을 일정하게 유지하고 과거 데이터를 효율적으로 조회하는 데 도움이 된다.
- 로그인 기록과 같이 장기간 보관이 필요한 데이터도 최신 몇 달 치만 중요하고 몇 년 전 패턴은 필요 없는 경우가 많으므로, 필요한 데이터를 180일 이내로 제한하고 매일 181일 이전 데이터를 삭제하여 데이터 개수를 일정 수준으로 유지할 수 있다.
- **주의사항**: `DELETE` 쿼리를 사용해도 디스크 사용량이 즉시 줄어들지 않을 수 있으며, 단편화가 발생할 수 있다. 최적화를 통해 단편화를 줄이고 디스크 사용량을 효율적으로 관리해야 한다.

### DB 장비 확장하기

DB에 부하가 증가하여 성능 문제가 발생하고 있다면, **DB 장비의 물리적인 성능을 확장**하는 것을 고려할 수 있다.

- **방법**: CPU를 교체하여 더 많은 CPU를 사용하거나 메모리를 증설하여 성능을 높일 수 있다.
- **Primary-Replica (주-복제) 구조**를 사용하여 조회 트래픽을 분산할 수 있다. 쓰기(INSERT, UPDATE, DELETE) 쿼리는 Primary DB를 통해 실행하고, 조회(SELECT) 쿼리는 Replica DB를 통해 실행하여 조회 처리량을 확장한다.
- **고려사항**: 장비 스펙을 변경하면 비용이 증가하지만, 서비스를 제대로 제공하지 못해 발생하는 비용보다 적을 수 있으므로 서비스를 유지하는 편이 낫다. DB 장비는 교체하면 성능이 눈에 띄게 향상되는 경우가 많다.

### 별도 캐시 서버 구성하기

DB만으로 모든 트래픽을 처리하기 어려울 경우, **별도의 캐시 서버를 구성하여 DB 부하를 줄일 수 있다**.

- **필요성**: 서비스가 급격히 성장하여 DB 트래픽 처리에 어려움을 겪을 때, 조회 성능 개선 방법 외에도 DB 트래픽을 처리하는 데 어려움이 있다면 캐시 서버 구성을 고려해야 한다.
- **이점**: 대부분의 대규모 데이터를 다루는 서비스는 캐시 서버를 기본적으로 사용한다. DB만으로는 모든 요청을 감당하는 데 한계가 있기 때문이다. 특히 대규모 조회 트래픽이 발생하는 경우 캐시 서버를 활용하면 DB 부하를 크게 줄일 수 있다.
- **구현**: 캐시 서버를 구축하고 활용하는 것은 서버 개발자나 인프라 엔지니어 입장에서 복잡하지만, 코드 수정에 비해 비용 대비 처리량 확장 효과가 크다면 합리적인 선택이 될 수 있다..

## 주의 사항

### 쿼리 타임아웃

길고 복잡한 쿼리는 실행 시간이 늘어나면서 서비스 응답 지연을 넘어 **쿼리 타임아웃**으로 이어질 수 있다.

- 예를 들어, **count(*) 쿼리**는 데이터가 증가할수록 실행 시간이 길어지며, 조건에 해당하는 모든 데이터를 탐색해야 하므로 심각한 성능 문제를 유발할 수 있다.
- **배치 쿼리**의 경우, 초기에는 30분이면 끝났던 쿼리가 데이터 증가에 따라 **수십 분에서 몇 시간까지 걸리게 될 수 있으며**, 특정 임계값을 넘기면 쿼리 실행 시간을 예측할 수 없을 만큼 길어져 타임아웃을 초래할 수 있다. 이러한 문제 발생 시 서비스 전체에 영향을 미칠 수 있으므로, 쿼리 실행 시간을 지속적으로 추적하고, 갑자기 길어진 쿼리의 원인을 찾아 해결해야 한다.

### 상태 변경 기능은 복제 DB에서 조회하지 않기

DB 부하를 분산하기 위해 **Primary-Replica (주-복제) 구조**를 사용할 수 있다. 이 구조에서는 Primary DB는 **쓰기(INSERT, UPDATE, DELETE) 쿼리**를 담당하고, Replica DB는 **조회(SELECT) 쿼리**를 처리하여 조회 처리량을 확장한다.

- 따라서 데이터의 상태를 변경하는 기능(쓰기 작업)은 Primary DB를 통해 실행되어야 하며, **복제 DB에서는 조회 기능만을 수행**하도록 설계해야 한다. 복제 DB에서 상태 변경 쿼리를 실행할 경우 데이터 불일치 및 아키텍처의 목적에 부합하지 않는 문제가 발생할 수 있다.

### 배치 쿼리 실행 시간 증가

배치 프로그램은 데이터를 일괄 처리하거나 집계, 생성하는 작업을 수행하는데, 이때 사용되는 집계 쿼리(예: `group by`, `count`, `sum`)는 데이터 양에 비례하여 실행 시간이 급증할 수 있다.

- **문제점**: 예를 들어, 월별 회원 통계 생성을 위해 한 달간의 데이터를 한 번에 집계하는 쿼리가 처음에는 30분 만에 끝났더라도, 데이터가 많아질수록 **몇 시간까지 길어질 수 있다**. 이는 특정 임계값을 넘기면 쿼리 실행 시간을 예측하기 어렵게 만들고, 메모리 사용량 증가와 함께 DB 성능 저하의 주원인이 될 수 있다.
- **해결책**
    - **배치 쿼리의 실행 시간을 지속적으로 추적**하여 쿼리가 갑자기 느려졌는지 확인하고 원인을 찾아야 한다.
    - **커버링 인덱스를 활용**하여 필요한 데이터를 빠르게 스캔하도록 한다.
    - **데이터를 일정한 크기로 나누어 처리**하는 방법을 사용한다. 예를 들어, 한 달 치의 접근 로그를 집계할 때, 하루 단위로 나눠 쿼리를 실행하고 그 결과를 합치거나, 심지어 10분 간격으로 나눠 작업을 실행할 수도 있다. 이 방법을 통해 쿼리 실행 시간을 단축하고 필요한 데이터를 안정적으로 생성할 수 있다.
    - **DB 장애 발생 시 데이터를 어떻게 처리할지 고려**해야 한다.

### 타입이 다른 칼럼 조인 주의

두 테이블을 조인할 때, 조인 조건에 사용되는 칼럼들의 **데이터 타입이 다르면 인덱스를 활용하지 못하여 성능 문제가 발생**할 수 있다.

- **예시**: `user` 테이블의 `userId` 칼럼이 `integer` 타입이고, `push` 테이블의 `receiverId` 칼럼이 `varchar` 타입일 때, `user.userId = p.receiverId`와 같이 조인하면 DB는 인덱스를 사용하지 못하고 **풀 스캔**을 수행하게 될 가능성이 높다. 이는 쿼리 실행 시간을 크게 증가시키고 DB 부하를 높이는 원인이 된다.
- **해결책**: 조인 조건을 사용하는 칼럼들은 **동일한 데이터 타입**으로 정의하는 것이 중요하다.

### 테이블 변경은 신중하게

DB 설계와 쿼리는 서비스 성능을 좌우하는 핵심 요소이므로, 테이블 구조나 인덱스 변경은 **매우 신중하게 접근**해야 한다.

- **인덱스 추가**: 인덱스를 너무 많이 추가하면 데이터 추가, 변경 시 인덱스 관리 비용(시간)이 증가하고, 인덱스 자체가 데이터이므로 메모리 및 디스크 사용량도 증가한다. **같은 칼럼에 중복으로 인덱스를 추가하지 않도록 주의**해야 한다. 기존에 존재하는 인덱스를 활용할 수 있는지 충분히 검토한 후 새로운 인덱스 추가 여부를 결정해야 한다.
- **비정규화**: 성능 개선을 위해 집계 칼럼을 추가하는 등의 비정규화는 데이터 중복을 야기하고 데이터 무결성 문제를 일으킬 수 있다. 따라서 비정규화를 적용할 때는 데이터 무결성 유지를 위한 철저한 관리가 필요하다.

### DB 최대 연결 개수

트래픽 증가를 감당하기 위해 API서버를 추가할 수 있다. 그런데 새로 추가한 API 서버에서 DB 커넥션 생성에 실패한다면 DB에 설정된 최대 연결 개수를 확인해봐야 한다.

### 실패와 트랜잭션 고려하기

안정적인 서비스 운영을 위해서는 **실패 상황에 대한 고려와 트랜잭션 관리**가 필수적이다.

- **동시성 문제**: 데이터를 미리 집계하는 방식에서 여러 클라이언트가 동시에 집계 칼럼을 업데이트할 경우 **동시성 문제**가 발생할 수 있다. 예를 들어, `update survey set answerCnt = answerCnt + 1 where surveyId = 1;`와 같은 쿼리가 동시에 실행될 때, `answerCnt` 값이 원하는 만큼 증가하지 않을 수 있다. 이러한 상황을 방지하기 위해 **DB에서 지정하는 트랜잭션 격리 수준**을 고려하여 원자적으로 처리되도록 해야 한다.
- **배치 처리 실패**: 배치 프로그램 실행 중 DB 문제 등으로 인해 데이터가 누락되거나 잘못 저장될 수 있다. 이 경우, **실패 시 복구 메커니즘**을 마련하고, 트랜잭션을 고려하여 데이터가 일정 크기로 나뉘어 안전하게 반영되도록 설계해야 한다. 과거에 DB 문제로 인해 일매출 데이터가 수집되지 않은 사례처럼, 데이터 유실은 심각한 서비스 문제로 이어질 수 있으므로, 장애 상황을 대비한 견고한 로직 구현이 중요하다.
